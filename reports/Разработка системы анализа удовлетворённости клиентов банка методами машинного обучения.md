| ---------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Бизнес-метрика               | Оптимизируется удержание клиентов — снижение ожидаемых потерь выручки от оттока. Классификатор по отзыву определяет эмоциональный окрас отзыва, что позволяет определить долю клиентов, которые имеют повышенный шанс уйти из банка. Обновление происходит по мере появления новых публикаций. Артефакты векторайзер и веса сохраняются локально.                                                                                                             |
| Эксплуатация                 | Предсказания заказчку поставляются в виде пакетного расчёта. Оркестратор ежедневно забирает новые порции данных, отправляет в модели и складывает предсказания (вероятность оттока, ожидаемый балл для каждого отзыва) в витрину данных DWH. Затем на основе данных из витрины данных формируются дашборты, где бизнес видит агрегированные KPI и списки клиентов для проработки.                                                                                          |
| Мониторинг                   | Дрейф данных вызывают такие внешние факторы, как изменение распределения длины отзывов, появление нового сленга/продуктов, сдвиг в пропорциях источников (например, резкое увеличение отзывов из ВК), изменение старых продуктов. Для решения проблемы дрейфа данных будет запускаться цикл переобучения. Условия запуска: по расписанию (раз в месяц) и по событию (падение метрик моделей ниже порога (после появления истинной разметки)).                              |
## 1.2 Выбор и анализ архитектурных подходов

Разрабатываемая система решает задачу бинарной классификация. На этапе инференса модель получает только текст отзыва и мета-данные. Результатом работы системы являются эмоциональная окраска нового отзыва, которые агрегируются в витрине данных и визуализируются в BI-дашбордах для бизнес-аналитиков и специалистов поддержки.

Поток данных начинается с внешних источников отзывов, откуда новые порции данных загружаются в сырой слой PostgreSQL. Далее Python-пайплайн, оркестрируемый через Airflow, выполняет очистку данных и переносит их в слой `staging`, где хранятся обработанные отзывы и извлечённые признаки. На этом же слое формируется материализованная таблица, объединяющая очищенные отзывы с истинной разметкой для обучения моделей. Обученные модели применяются к новым порциям данных в режиме инференса, а предсказания вместе с версией модели записываются в слой обработанных данных (`staging`). Витрина данных строится на таблицах слоя обработанных данных. BI-система Redash подключается к витрине по SQL и строит дашборды с ключевыми показателями: долей клиентов в зоне риска, ожидаемыми потерями выручки, распределением прогнозируемых оценок. По мере поступления истинной разметки (с задержкой в несколько дней или недель) слой обработанных данных обогащается фактическими значениями, что позволяет рассчитывать метрики качества модели и принимать решение о переобучении по расписанию или при деградации метрик.

| Версионирование данных | **Git**          | DVC, Git LFS                        | Датасет 30 МБ — DVC требует внешнего хранилища и усложняет развёртывание; LFS избыточен на таком объёме.                                                                               |

Выбранный стек снижает стоимость сопровождения и гарантирует воспроизводимость за счёт устранения избыточных слоёв и фиксации версий всех компонентов. Единая СУБД PostgreSQL хранит данные всех трёх уровней (raw/staging/marts) в одной системе с разделением через схемы, что исключает синхронизацию между хранилищами и риск рассогласованности. Airflow централизует управление зависимостями между шагами пайплайна: отказ этапа фиксируется в журнале и перезапускается автоматически, а сам DAG описывается в Python и версионируется через Git, что исключает расхождение логики между окружениями. BI-система Redash работает напрямую через SQL к витрине, устраняя дополнительный слой выгрузки. Все компоненты имеют открытые лицензии и упакованы в Docker-контейнеры: docker-compose поднимает PostgreSQL, Airflow и Redash в фиксированных версиях на любой машине, исключая ошибки. Git версионирует и код, и данные, что позволяет воспроизвести любой эксперимент. SQL-скрипты в папке `sql/` воспроизводят структуру базы данных из кода, а не через ручное создание в GUI, гарантируя идентичность физической модели на любом окружении.

## 2.3 Требования к качеству данных и ключевые показатели

| №   | Признак(и)       | Требование                                                        | Действие при нарушении                                        |
| --- | ---------------- | ----------------------------------------------------------------- | ------------------------------------------------------------- |
| 1   | `review_text`    | Не пустой и не короче 20 символов                                 | Карантин                                                      |
| 2   | `review_text`    | В системе нет отзыва с таким же текстом                           | Карантин                                                      |
| 3   | `review_dttm`    | Парсится как дата, не в будущем, не старше 3 лет от даты порции   | Карантин                                                      |
| 4   | `product`        | Значение из фиксированного справочника, без регистровых вариантов | Приведение к справочнику; значение вне справочника — карантин |
| 5   | `review_source`  | Значение из справочника площадок                                  | Карантин                                                      |
| 6   | `review_emotion` | Значение из двух допустимых: позитивный или негативный            | Карантин                                                      |

**Карантин** — отдельная таблица (схема `quarantine`), куда попадает каждая исключённая запись целиком вместе с причиной отклонения и датой порции. Ничего не удаляется: разбор выполняет человек, после чего запись либо правится и возвращается в поток, либо закрывается.


| Показатель | Как рассчитывается | Использует модель | Какое решение помогает принять |
|---|---|---|---|
| Доля негативных отзывов | Отзывов с `p(негатив) ≥ 0.5` / отзывов с текстом за порцию | Да | Масштаб претензионного потока, план загрузки поддержки |
| Топ продуктов по прогнозному негативу | Доля `p ≥ 0.5` в разрезе `product`, продукты с n ≥ 30 | Да | Куда направить продуктовую команду |
| Дельта доли негатива к предыдущей порции | `share_t − share_(t−1)`, п.п. | Да | Триггер разбора инцидента и внепланового переобучения |
| Доля карантина | Записей в карантине / записей порции | Нет | Качество входных данных, разбор с поставщиком |
| Доля известной разметки | Записей с заполненной `review_emotion` / всего записей | Нет | Задержка разметки, готовность к переобучению |

```mermaid
sequenceDiagram
    autonumber
    participant SRC as Источник
    participant AF as Airflow
    participant ING as Приём данных
    participant DB as PostgreSQL
    participant PREP as Подготовка данных
    participant ML as ML-модуль

    AF->>SRC: Запрос новой порции
    SRC-)ING: Два файла порции (CSV): признаки и разметка
    ING->>DB: Записать порцию в raw
    DB-->>ING: Порция сохранена
    ING-->>AF: Порция загружена (n записей)

    AF->>PREP: Запустить проверку качества
    PREP->>DB: Прочитать порцию из raw
    DB-->>PREP: Записи порции
    PREP->>DB: Записать отбракованные в quarantine
    PREP->>DB: Записать очищенные данные и признаки в staging
    PREP-->>AF: Отчёт о качестве (принято / карантин)

    AF->>ML: Запустить пакетный инференс
    ML->>DB: Загрузить артефакты модели и model_version
    DB-->>ML: Векторайзер, веса
    ML->>DB: Прочитать признаки из staging
    DB-->>ML: Матрица признаков
    ML->>DB: Записать предсказания в staging.ml_predictions
    ML-->>AF: Инференс завершён (n предсказаний)

    AF->>KPI: Пересчитать ключевые показатели
    KPI->>DB: Прочитать предсказания и известную разметку
    DB-->>KPI: Данные для КП и метрик
    KPI->>DB: Записать КП в витрину с меткой порции
    KPI-->>AF: Показатели пересчитаны
```

Новая порция попадает в слой сырых данных, после чего те же шаги обработки, что и при обучении, переносят её в слой обработанных данных и обогащают предсказаниями модели, а витрина данных строится на таблицах слоя обработанных данных. Пересчёт ключевых показателей выполняется сразу после инференса или после получения разметки и пишется в витрину с меткой порции, поэтому каждый запуск добавляет новую точку динамики, не изменяя предыдущие. Redash читает витрину напрямую по SQL, так что панель обновляется вместе с данными без отдельного слоя загрузки.

# ОБУЧЕНИЕ И СРАВНЕНИЕ ML-МОДЕЛЕЙ

## План экспериментов

### Метрики

Бизнес-метрика проекта состоит в снижении ожидаемых потерь выручки от оттока. Классификатор по тексту отзыва оценивает вероятность негатива, что позволяет видеть долю клиентов с повышенным риском ухода и приоритет обработки обращений. Метрики машинного обучения выбираются по тому, насколько они отражают эту величину.

Основная метрика ROC-AUC. Она измеряет качество ранжирования отзывов по вероятности негатива и не зависит от выбранного порога, поэтому по ней сравниваются модели до того, как определена цена ошибок и рабочий порог. Ранжирование связано с бизнес-метрикой напрямую: очередь на обработку и расчёт доли негатива строятся по упорядоченным вероятностям.

Вспомогательные метрики PR-AUC и F2-мера. PR-AUC показывает качество выделения негативных отзывов при несбалансированных классах и опирается на долю негатива как базовую линию, поэтому она приводится вместе с этой долей в проверочном блоке. F2-мера при фиксированном пороге 0,5 отражает приоритет полноты над точностью, потому что пропуск недовольного клиента обходится дороже ложного срабатывания.

Brier Score в сравнении моделей не участвует и применяется на этапе выбора рабочего порога как мера калибровки вероятностей.

### Стратегия валидации

Применяется временное разбиение. Записи сортируются по дате публикации отзыва, очищаются от пустых текстов, текстов короче 20 символов и повторов, после чего первые 80 процентов по времени образуют обучающую часть, последние 20 процентов отложенную тестовую. При текущем объёме это 26 321 и 6 581 запись. Тестовая часть не участвует в выборе модели и в подборе гиперпараметров и применяется один раз для итоговой оценки.

Случайное разбиение не используется. Оно допускает попадание более поздних отзывов в обучение, а более ранних в проверку, из-за чего оценка перестаёт отражать работу модели на будущих данных.

### Схема кросс-валидации

Внутри обучающей части применяется TimeSeriesSplit на пять блоков с расширяющимся окном. Проверочный блок всегда следует за обучающими данными и содержит 4 386 записей, около 16,7 процента обучающей части, а обучающее окно начинается с начала истории и растёт от 4 391 до 21 935 записей.

Схема соответствует временной зависимости данных: на каждом шаге модель обучается только на прошлом и проверяется на непосредственно следующем за ним периоде, что повторяет порядок переобучения в эксплуатации.

По каждому блоку записываются ROC-AUC, PR-AUC, F2 при пороге 0,5 и доля негатива, итогом считается среднее значение и стандартное отклонение по блокам.

### Стратегия исключения утечек

Признаки, которые появляются после публикации отзыва или прямо раскрывают целевую переменную, в модель не включаются. 

Оценка параметров предобработки выполняется только внутри обучающего фрагмента. TF-IDF, кодирование категориальных признаков и масштабирование объединены с моделью в Pipeline и обучаются заново на каждом блоке кросс-валидации, поэтому проверочные данные не влияют на словарь и веса. Оценка этих параметров по всей выборке до разбиения дала бы модели сведения о проверочных записях.

Дубликаты текстов удаляются до разбиения, поэтому одинаковые отзывы не попадают одновременно в обучение и проверку. Повторы по id_client утечкой не являются, так как при временном разбиении все отзывы клиента в проверочном блоке опубликованы позже его отзывов в обучающем, и модель работает только с прошлым.

### Выбор модели

Базовое решение задаёт нижнюю границу качества, ниже которой модель не принимается в систему. Используются два варианта. Первый относит все отзывы к преобладающему классу, позитивному. Доля верных ответов при этом составляет 62,6 процента, ROC-AUC равна 0,5, а F2-мера равна 0, поскольку негативные отзывы не находятся вовсе. Второй опирается на проверенную гипотезу 1, по которой негативные отзывы длиннее позитивных. Отзыв относится к негативу, если его длина превышает медиану обучающей части, 439 символов. На обучающей части правило даёт точность 0,482, полноту 0,644 и F2-меру 0,603. Модель считается пригодной, если превосходит оба базовых решения по ROC-AUC и F2-мере на кросс-валидации.

Порог длины считается только по обучающей части, поэтому в проверочные блоки сведения о их длинах не попадают.

Итоговая модель выбирается по наибольшему среднему значению ROC-AUC на кросс-валидации. Если различия между лидерами не превышают 0,005, предпочтение отдаётся более простой и быстрой модели, потому что такой разрыв лежит в пределах разброса между блоками.

Дополнительными условиями выбора служат PR-AUC с учётом доли негатива в блоке и F2 при пороге 0,5, поскольку модель не должна улучшать ранжирование за счёт качества на рабочем пороге. Модель, которая не превосходит базовое решение по ROC-AUC и F2, в качестве итоговой не рассматривается.

Выбранная модель обучается на всей обучающей части с фиксированным начальным значением генератора, сохраняется вместе с параметрами и описанием и воспроизводится одной командой. Выбранная схема даёт сопоставимую оценку качества для всех семейств и исключает попадание сведений из проверочных блоков в обучение, поэтому результаты кросс-валидации сравнимы между собой и переносятся на поток новых отзывов.

## Обоснование семейств моделей

Семейства моделей различаются требованиями к предобработке и поведением на разреженных текстовых признаках. Сопоставление приведено в таблице.

| Модель | Требования к предобработке | Сильные стороны | Ожидаемые проблемы на данных |
|---|---|---|---|
| Логистическая регрессия с L1 и L2 | полный TF-IDF, масштабирование числовых признаков | интерпретируемость, скорость, устойчивость на разреженных данных | не учитывает взаимодействия слов, слабее на нелинейных конструкциях |
| k ближайших соседей | снижение размерности через SVD, масштабирование | простая нелинейная модель | на разреженном TF-IDF расстояния теряют смысл, медленный на десятках тысяч записей |
| Дерево решений | SVD, масштабирование не требуется | интерпретируемость, нелинейность | переобучается без ограничения глубины, плохо делит разреженный текст |
| Наивный байесовский классификатор | полный TF-IDF, масштабирование не требуется | скорость, работает при малом числе наблюдений | предположение о независимости признаков, вероятности плохо калиброваны |
| Случайный лес | SVD, масштабирование не требуется | устойчивость к переобучению, нелинейность | на разреженном тексте проигрывает линейным моделям, дороже по памяти |
| Градиентный бустинг | SVD, масштабирование не требуется | нелинейность, обычно высокая точность | требователен к подбору гиперпараметров, медленнее, вероятности требуют калибровки |

Ожидается, что лучшей окажется логистическая регрессия на полном TF-IDF. Сигнал негатива выражен в лексике и близок к линейному по признакам, а размерность текстовых признаков слишком велика для деревьев и соседей. Ансамбли могут сократить разрыв, но существенного превосходства над линейной моделью не ожидается.

## Учет экспериментов

Эксперименты выполняются прогоном по исторической части (history.csv) в директории data/incoming, логика обучения вынесена в модули src/models.py и src/experiments.py. Прогон вызывает готовые функции и не содержит собственного кода подготовки данных, поэтому сравнение моделей воспроизводится по коду и по сохранённым записям запусков.

Пайплайн подготовки задан одной структурой. Он включает TF-IDF по тексту отзыва, one-hot кодирование источника, три числовых признака и классификатор на последнем шаге. TF-IDF ограничен 30 000 признаками, использует униграммы и биграммы, порог частоты 2 и сублинейное взвешивание. Для нелинейных семейств текстовое представление заменяется усечённым через сингулярное разложение до 100 компонент, это задаётся параметром text_repr. Кодирование источника выполнено так, что неизвестная категория в новой порции не вызывает ошибки. На каждый блок кросс-валидации создаётся новый экземпляр пайплайна, поэтому словарь TF-IDF и параметры кодирования оцениваются только на обучающем фрагменте блока. Каждый эксперимент добавляет строку в журнал experiments/log.jsonl. В строке фиксируются идентификатор запуска, дата и время, семейство, гиперпараметры, текстовое представление, признак использования числовых признаков, схема валидации, число записей в наборе, в обучающей и тестовой частях, источник данных, начальное значение генератора, метрики каждого блока с числом записей и временем обучения, средние значения и стандартное отклонение по блокам. Перебираемые значения для подбора задаются в модуле models и в журнал не пишутся. Сводная таблица runs.csv и таблица по блокам folds.csv собираются из журнала функцией build_tables, поэтому сводка всегда соответствует исходным записям. В runs.csv одна строка на эксперимент со средними значениями и разбросом метрик, в folds.csv одна строка на блок кросс-валидации. Каталог версионируется вместе с кодом, что позволяет восстановить любой эксперимент по коммиту и файлу данных.

После сравнения моделей оформляется запись о решении в experiments/decision.md. В ней указываются выбранный идентификатор запуска, значения метрик, по которым сделан выбор, и таблица остальных запусков. Эта запись служит ответом на вопрос, почему выбрана конкретная модель, и используется при подготовке отчёта. Итоговая модель сохраняется как Pipeline целиком, векторайзер и классификатор в одном объекте joblib в каталоге models. Рядом размещается model_v1.json с версией, датой, ссылкой на запуск, гиперпараметрами, набором признаков, числом записей, версией scikit-learn, метриками на кросс-валидации и именем файла артефакта, а указатель models/current.json задаёт действующую версию для инференса. Откат сводится к переключению указателя на предыдущую версию.

Итоговая модель обучается отдельным скриптом src/train_final.py на всей обучающей части с фиксированным начальным значением генератора, поэтому артефакт не зависит от порядка запусков и собирается одной командой. Журнал запусков и отдельное описание модели позволяют воспроизвести любой эксперимент по сохранённым параметрам и вернуться к предыдущей версии переключением указателя, не повторяя обучение.

## Реализация пайплайна и признаков

Подготовка данных и модель объединены в объект Pipeline. Первым шагом рассчитываются признаки, вторым применяется ColumnTransformer, последним стоит классификатор. Внутри ColumnTransformer три ветви: числовые признаки со стандартизацией, текст отзыва с TF-IDF на 30 000 признаков с униграммами и биграммами, источник с one-hot кодированием. Для нелинейных семейств текстовое представление сжимается усечённым сингулярным разложением до 100 компонент, потому что на разреженных векторах расстояния и пороговые правила теряют смысл.

Три признака рассчитываются из текста отзыва. `words_cnt` равно числу слов при разбиении по пробелам. `avg_word_len` равно отношению числа непробельных символов к числу слов. `exclaim_cnt` равно числу восклицательных знаков и отражает интенсивность высказывания. Признак `product` в модель не включён, поскольку приходит вместе с разметкой и на инференсе недоступен.

Обработка новой порции выполняется двумя DAGами. `review_ingestion` запускается по расписанию, просматривает каталог `data/incoming/features` в порядке `history.csv`, затем `batch_N.csv` по возрастанию номера, пропускает файлы, уже загруженные по контрольной сумме, регистрирует новую порцию и записывает строки в `raw.review`, после чего порция получает статус `processing`. `staging` забирает порции в этом статусе, применяет правила качества, заполняет `staging.review_clean` и карантин, собирает `staging.training_set` тем же кодом, что используется при обучении, и переводит порцию в статус `done`. Поток разметки устроен так же: `enrichment_ingestion` читает каталог `data/incoming/labels` и загружает порцию в `raw.review_enrichment` только после того, как отзывы этой порции уже загружены; `staging` проверяет разметку и дополняет `staging.training_set`. Упавшая порция остаётся в статусе `processing`, поэтому следующий запуск повторяет её без ручного вмешательства.

Исходная выгрузка разделена на два набора с совпадающими именами файлов. В каталоге `features` остаются ключи `id_client` и `review_dttm`, текст отзыва и площадка, то есть поля, из которых строятся признаки модели. В каталоге `labels` остаются ключи, продукт и целевая переменная `review_emotion`. Продукт в модель не входит, но остаётся в разметке, потому что его проверяют правила качества. Остальные девятнадцать колонок выгрузки не используются ни на одном шаге и в наборы не включены.

Повторяемость проверена двумя последовательными запусками обучения на одних данных. Вероятности на первых 500 записях совпали, максимальное расхождение равно 0,000000, хеши SHA-256 сохранённых артефактов совпали.

## Базовое решение и линейные модели

Наиболее частый класс даёт долю верных ответов 0,626, ROC-AUC 0,500 и нулевую полноту. Правило длины с порогом 439 символов даёт точность 0,482, полноту 0,644, F2-меру 0,603 и ROC-AUC 0,615.

Для линейной модели обучены два варианта регуляризации. При сильной регуляризации L1 с C = 0,001 ненулевых коэффициентов остаётся 2 из 30 021 при качестве 0,730. С ростом C число ненулевых коэффициентов увеличивается, при C = 0,1 их 57. Начиная с C = 1 качество обеих моделей выходит на плато около 0,998. Модель L2 сохраняет все коэффициенты и при одинаковых C не уступает L1 по качеству. Модель L2 показывает средний ROC-AUC 0,993 на кросс-валидации.

Наибольший положительный вес имеют «прошу», «не рекомендую» и «заблокировали», наибольший отрицательный вес имеют «спасибо», «быстро» и «вернули». Знаки коэффициентов согласуются с выводами разведочного анализа. Числовые признаки влияют слабее слов, вес числа слов положителен, то есть негативные отзывы длиннее, веса средней длины слова и числа восклицательных знаков отрицательны.

## Модели классификации и ансамбли

Кроме линейной модели обучены наивный байесовский классификатор со средним ROC-AUC 0,994, метод k ближайших соседей с 0,966, дерево решений с 0,941, случайный лес с 0,989 и градиентный бустинг с 0,993.

Зависимость качества дерева решений от глубины показывает переобучение. До глубины 6 качество растёт на обеих выборках, затем на обучающей части оно достигает 0,998, а на проверочной падает до 0,930 при глубине 15.

Польза новых признаков оценена сравнением моделей на исходном наборе признаков и на наборе с добавленными признаками. Для логистической регрессии ROC-AUC равен 0,994 без признаков и 0,993 с признаками; для градиентного бустинга ROC-AUC равен 0,992 без признаков и 0,993 с признаками. Изменение качества не превышает 0,001 и лежит в пределах разброса между блоками. Признаки сохранены, поскольку не ухудшают качество за пределами разброса и дают понятные характеристики текста.

## Подбор гиперпараметров

Перебор выполнен для двух лучших семейств; для наивного байесовского классификатора лучшим набором оказался сглаживание 0,1, качество изменилось с 0,994 до 0,995; для логистической регрессии лучшим набором оказался C = 10, L2, качество изменилось с 0,993 до 0,995.

## Сравнение и выбор итоговой модели

Итоговой моделью выбрана логистическая регрессия с параметрами C = 10 и регуляризацией L2. Средний ROC-AUC на кросс-валидации равен 0,995 плюс-минус 0,002, PR-AUC 0,991, F2-мера при пороге 0,5 0,973. Различие с ближайшим вариантом не превышает 0,005, поэтому по правилу выбора предпочтение отдано более простой и быстрой модели.

Гипотеза о превосходстве линейной модели подтвердилась. Модель сохранена в models/model_v1.joblib вместе с описанием, содержащим версию, гиперпараметры, метрики и версию scikit-learn.
